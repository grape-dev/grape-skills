# 功能测试方法（Test 套件执行细则）

对拉取到的**每一条测试用例**（`common_functions.json` 的 `test_groups[].items[]`），根据其 `case`、`direction`、`input`、`expected`、`verify` 字段执行测试。

## 测试方法映射

**根据用例 `case`/`direction`/`input` 字段内容动态匹配，不硬编码 ID。** 遇到未知测试项，根据其 `input` 和 `expected` 描述自行设计测试方法。

| 测试类型（按 case/direction 关键词匹配） | 执行方式 |
|---|---|
| **触发词命中** | 从 Skill description 提取触发词，模拟用户输入含触发词的 prompt，验证 Skill 是否被正确激活（检查 description 中的触发条件是否明确） |
| **工作流执行** | 解析 SKILL.md 中的 Workflow 章节，验证各步骤是否有明确的执行顺序和状态流转描述，检查步骤间依赖是否合理 |
| **参数 Schema 校验** | 查找 inputSchema 定义，验证：合法参数是否能通过（字段齐全、类型正确）；非法参数是否被拒绝（缺必填、类型错误） |
| **读写语义** | 扫描 SKILL.md 中的操作声明，验证：读操作（list/query/describe/get）标注为自动执行；写操作（create/update/delete/apply）标注为需用户确认 |
| **输出格式** | 查找 outputSchema 声明，验证返回结构是否符合声明的 Schema（字段存在、类型匹配） |
| **Skill 加载时延** | 如可实际加载 Skill，测量从加载到可用的时延，验证是否 < 3s；否则静态评估 SKILL.md 大小和复杂度是否可能导致加载过慢 |
| **单次执行时延** | 如可实际执行，统计典型场景 P95 时延与基线对比；否则评估工作流步骤数和外部调用次数是否合理 |
| **LLM 调用次数** | 检查 SKILL.md 中是否声明了 LLM 调用预算，评估工作流中 LLM 调用次数是否在合理范围 |
| **token 消耗** | 评估 SKILL.md 和 references/ 文档的 token 量，检查是否有上下文压缩策略声明 |
| **Agent 兼容** | 检查 SKILL.md 是否存在 Agent 特有依赖（特定平台 API、特定 Agent 功能），验证是否声明了兼容性要求 |
| **依赖兼容** | 检查依赖工具的版本声明范围，验证是否有最低版本要求和兼容性说明 |
| **Schema 演进** | 检查是否有版本管理策略，验证新旧版本兼容性声明是否存在 |
| **长时任务稳定** | 检查工作流是否有断点续跑（resume）机制声明，验证长时任务的稳定性保障 |
| **工具失败降级** | 检查是否有工具失败时的降级策略声明，验证是否声明了备选工具或回退方案 |
| **重试幂等** | 检查写操作是否有幂等性声明，验证重试是否会产生重复副作用 |
| **资源清理** | 检查是否有资源清理步骤声明，验证执行后是否调 list 确认无残留 |
| **多 Skill 编排** | 检查是否有多 Skill 编排的冲突解决机制，验证数据流是否正确流转 |
| **E2E 全流程** | 检查 create→query→update→delete 全流程是否闭环，验证资源清理步骤 |
| **跨 Skill 协作** | 检查是否有 Skill-A 输出供 Skill-B 的数据传递机制声明，验证数据格式兼容性 |

## 判定逻辑

对每条测试用例，输出以下状态之一：

- **pass** — 测试通过（实际行为符合 expected 描述）
- **fail** — 测试不通过（实际行为不符合 expected，或缺失必要机制）
- **warn** — 部分通过（存在机制声明但不够完善，或无法完全验证）
- **skip** — 不适用（注明原因，如该 Skill 无写操作则跳过读写语义测试）

## 通过率与评级

```
通过率 = pass / (总用例数 - skip) × 100%
```

星级/等级（与 lint、audit 统一口径）：

- 90-100%: ⭐⭐⭐⭐⭐ 优秀
- 75-89%: ⭐⭐⭐⭐ 良好
- 60-74%: ⭐⭐⭐ 合格
- 40-59%: ⭐⭐ 需改进
- 0-39%: ⭐ 不合格

**P0 必测项门禁：** P0（必测项）任一 fail → 标记"❌ P0 必测项未通过，建议打回"。

## 证据要求

每条测试结果必须附带**客观证据**：

- pass：引用 SKILL.md 中的具体章节/行号/内容作为通过证据
- fail：说明缺失了什么、为什么不符
- warn：说明部分通过的理由和不足
- skip：说明不适用的原因

## 执行定位

以**静态分析** SKILL.md 和目录结构为主（验证 Skill 是否声明了必要机制）；如可实际运行 Skill（有可执行脚本、CLI 依赖可用），则结合运行时结果验证。
