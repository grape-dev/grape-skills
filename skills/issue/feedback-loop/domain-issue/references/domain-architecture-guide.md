# 领域架构设计指南（拆角色 / 定流程 / 配信号）

> 配套 `skills/domain-issue/SKILL.md`。本指南给出设计方法论，并以「法务 Swarm（LegalSwarm）」为贯穿示例逐步演示设计输出，供任意领域（医疗/金融/政务/工业/教育…）套用。

## 一、领域画像四要素（阶段 1 澄清用）

| 要素 | 判断问题 | 法务示例（达标） | 不达标示例 |
|------|---------|----------------|-----------|
| 目标用户 | 谁在用？ | 公司法务部 / 律所律师 / 企业法务专员 | "律师" |
| 领域任务 | 用它完成哪些日常环节？ | 合同审查、法律检索、案件管理、文书生成、合规咨询 | "法律工作" |
| 交付形态 | 产出以什么形式落地？ | 审查意见书（含风险点/修改建议）、检索报告、起诉状/合同范本、案件台账 | "给建议" |
| 验收标准 | 怎么算做对了？ | 合同审查覆盖必备条款清单；文书符合法律文书格式 | "能用" |
| 功能模块 | 前端左侧导航要哪些可点页面？后端落什么数据？ | 案件管理/文书起草/合同审查/法规检索/合规检查/法务团队，全部 RPC 落库 | "做个页面" |

四要素 + 功能模块齐全 → 进入设计；缺失 → 提问澄清（≤3 轮）。

## 二、设计四步法总览（相对 eduSwarm 增加「划功能」）

```
第一步：划功能 → 哪些功能做成前端可点页面？每个页面背后 RPC 落什么数据？
第二步：拆角色 → 谁参与？各自的专业边界是什么？
第三步：定流程 → 谁先谁后？产出怎么流转？
第四步：配信号 → Agent 之间怎么交接？什么时候算完成？
```

## 三、第一步（先做）：划功能（领域功能清单）

> 参考基线仓库法务实现：`LegalWorkbenchPanel` + `legal.*` RPC 组成《域功能清单》。

```markdown
| # | 功能名 | 前端导航 key | 页面组件 | 后端 RPC | 落库表 |
|---|--------|-------------|---------|---------|--------|
| 1 | 案件管理 | `legalCase` | `LegalCasePanel` | legal.case.list/create/get | cases |
| 2 | 文书起草 | `legalDocument` | `LegalDocumentPanel` | legal.document.draft/save/list | documents |
| 3 | 合同审查 | `legalContract` | `LegalContractPanel` | legal.contract.review/list | contract_reviews |
| 4 | 法规检索 | `legalSearch` | `LegalSearchPanel` | legal.search_law | search_logs |
| 5 | 合规检查 | `legalCompliance` | `LegalCompliancePanel` | legal.compliance.check | compliance_reports |
| 6 | 法务团队 | `legalTeam` | `LegalTeamPanel` | legal.team.list / legal.skills.list | （配置驱动）|
```

- 每个功能「前端 + RPC + 落库」三件套，缺一不可（只读类注明）。
- 功能清单将直接决定 domain-coding 的页面组件、`<domain>Api.ts` 与 backend RPC 实现顺序。

## 四、第二步：拆角色（LegalSwarm 示例）

**原则：每个 Agent 只做一件事做到极致；LEADER 只调度不干活。**

| Agent | 唯一职责 | 不做什么 | 对应 EduSwarm 原型 |
|-------|----------|----------|-------------------|
| LEADER 法务主管 | 理解需求→判断复杂度→组队/直调→汇总审核 | 不审合同、不写文书 | 教研组长 |
| 合同审查师 contract-reviewer | 合同审查：必备条款/风险条款/修改意见/审查意见书 | 不写诉讼文书 | 课件师 |
| 法律检索师 legal-researcher | 法条/案例/裁判规则检索，输出标注来源的检索报告 | 不分析具体案件 | 学情分析师（数据侧） |
| 文书引擎师 legal-drafter | 按文书类型生成起诉状/答辩状/合同/律师函/合规意见书 | 不评风险等级 | 出题官 |
| 案件管理师 case-manager | 案件信息归档、时间轴、证据清单、流程状态更新 | 不给出法律意见 | 班级/课堂管理 |
| 合规审查师 compliance-reviewer | 合规风险初筛、监管要点核对、合规清单 | 不深度检索 | 批改师（质检侧） |
| 法律顾问 legal-counsel | 面向业务人员的一对一法律咨询与答疑 | 不批量处理案件 | 答疑教师 |

知识图谱师等价物（如法条图谱）→ 待开发，不进团队、不被调度。

**角色拆解决策原则**：
1. 角色数控制在 LEADER + 4~8 个（太多则调度链路冗长，太少则职责模糊）。
2. 每个角色必须有至少 1 个可落地的领域能力 RPC（`legal.contract.review` 等）。
3. "主生产"角色（审查/检索/文书）与"质检"角色（合规/审校）分离，形成质量闭环。

## 五、第三步：定流程（任务分类矩阵）

**不是所有任务都要组队。** LEADER 必须先做复杂度判断：

| 任务类型 | 判定 | 处理方式 | 法务示例 |
|---------|------|---------|---------|
| 简单任务 | 单次单产出 | LEADER 直接调用领域 RPC 秒级完成，**不组队** | "把这份采购合同过一遍风险点" → 直调 contract-reviewer 能力 |
| 中等任务 | 2-3 步线性 | 按序串联调用，每步入库 | "审查合同 + 给修改意见书" → 审查→意见书 |
| 复杂任务 | 多环节依赖、需迭代 | **组队**：分解→派发→汇总审核 | "新项目全套法律文件：合同+合规评估+风险防控方案" → 组队 |
| 长周期任务 | 跨天/跨案卷 | 组队 + 持久化跟进 | "案件全周期管理：立案→证据→庭审材料→结案归档" |

LEADER 开局应亮出团队名单与判断（"这个任务我直接处理 / 需要组成法务团队协作"），避免用户误以为团队没组起来。

## 六、第四步：配信号（领域数据模型 + 交接协议）

**最重要的原则：AI 对话产出必须"落地"，交付物要有 ID 和位置。**

### 5.1 领域数据模型（后端 SQLite 表）

| 对象 | 字段要点 | 入库位置 |
|------|---------|---------|
| 案件 matter | id、名称、案由、当事人、承办人、状态、时间轴 | `data/<domain>/matters.db` |
| 合同审查任务 contract_review | id、合同文件、审查状态、风险条数、意见书路径 | 同上 |
| 法律检索报告 research_report | id、检索主题、法条/案例来源列表、报告路径 | 同上 |
| 文书文档 legal_doc | id、类型（起诉状/合同/律师函…）、内容、状态 | 同上 |
| 合规清单 compliance_checklist | id、监管要点、风险等级、整改建议 | 同上 |

### 5.2 交接协议（复用 EduSwarm 验证过的信号约定）

1. **单发言人**：只有 LEADER 直接对用户说话，成员只向组长汇报、由组长转达。
2. **一次一个成员**：激活成员 → 等 `CONTROL_RETURN`（含产出摘要 + 产出ID/路径）→ 再切换，严格串行。
3. **产出入库**：成员完成任务必须走领域 RPC 入库（如 `legal.contract.review` save_to_db=true），交付 = `{产出ID, 路径}`，禁止只输出文本。
4. **数据联动**：子环节产出自动关联父对象（如审查意见书自动关联合同 ID 与案件 ID），任何面板可溯源整条法务链。
5. **降级路径**：成员失败 → LEADER 兜底直调领域能力，不卡死流程。

### 5.3 领域化工作流（LegalSwarm 示例流水线）

```
用户需求 → LEADER 判断复杂度
   简单 → 直调 legal.contract.review / legal.research.search
   复杂 → 组队：
     合同审查师（审查+意见书入库）
        → 法律检索师（法条案例检索报告入库）
          → 合规审查师（合规清单入库）
            → LEADER 汇总审核 → 交付：{案件matter_id + 各报告ID}
```

## 七、领域 RPC 命名空间设计

统一 `<domain>.<业务域>.<动作>`，与扩展 `extension.py` 注册一一对应（法务先例实际立项如下）：

| 命名空间 | 法务示例（基线仓库实际已实现） | EduSwarm 对应 |
|---------|------------------------------|--------------|
| `<domain>.case.*` | `legal.case.create` / `legal.case.list` / `legal.case.get` / `legal.case.update` | `edu.class.*` |
| `<domain>.contract.*` | `legal.contract.review` / `legal.contract.list` | `edu.courseware.*` |
| `<domain>.document.*` | `legal.document.draft` / `legal.document.save` / `legal.document.list` | `edu.assignment.*` |
| `<domain>.search_law` | `legal.search_law`（检索法条） | `edu.analytics.*` |
| `<domain>.compliance.*` | `legal.compliance.check` | `edu.grading.*` |
| `<domain>.team.*` | `legal.team.list`（团队信息，供前端"法务团队"页） | `edu.team.*` |
| `<domain>.skills.*` | `legal.skills.list`（技能清单，供前端与「能做啥」回答） | `edu.skills.*` |
| `<domain>.agent.config.*` | Agent 配置管理 | `edu.agent.config.*` |

## 八、Demo 场景（LEADER 开局示例文案，法务版）

```
我的法务团队已就位：合同审查师、法律检索师、文书引擎师、案件管理师、合规审查师、法律顾问 6 位成员。
这个任务我直接处理 / 需要组建法务团队协作。

示例任务话术：
- 简单："审一下这份 NDA，标出风险条款" 
- 复杂："为 XX 并购项目出一套法律文件：合同审查 + 合规评估 + 风险防控方案"
- 长周期："接手这个劳动纠纷案件，管理立案到结案全流程"

用户问「你能做什么？」时（回答 = 平台能力 + 领域能力，不能只讲平台或只讲领域）：
- 平台能力：多 Agent 协作/文件处理/联网检索/工作台对话等（沿用模板描述）
- 领域能力（本项目）：案件管理（建档/列表/详情）、文书起草（模板→初稿）、合同审查（风险点+意见书）、
  法规检索（带来源）、合规检查（清单）、法务团队（成员/技能展示）
- 参考实现：`legal.skills.list` + `legal.team.list` RPC 提供能力清单数据驱动回答
```

## 九、其他领域速查（换领域时替换"法务"细节）

| 领域 | LEADER 角色 | 主生产 Agent | 质检 Agent | 数据对象 |
|------|------------|-------------|-----------|---------|
| 医疗 | 医务主管 | 病历质控/检验报告/健康科普 | 合规药师 | 患者/病历/报告 |
| 金融 | 风控主管 | 信贷尽调/研报撰写/投教内容 | 合规审查 | 客户/尽调/研报 |
| 政务 | 政务专员 | 材料代填/政策问答/公文起草 | 审核校核 | 事项/材料/办件 |
| 工业 | 制造主管 | 工艺卡片/质检规范/设备维护 | 安全审核 | 产线/工单/规范 |

> 无论什么领域，三步法（拆角色→定流程→配信号）与信号协议（落地入库、CONTROL_RETURN、单发言人、禁止嵌套组队、简单不组队）不变，变的只是角色表、RPC 与数据表。
