# 需求引导与 Issue 审视指南（VOD-Strict）

> 配套 `skills/vod/vod-strict/SKILL.md`。覆盖：需求类型判定信号、先调查原则、功能四要素、Bug 六要素、结构化模板、strict A2A 动态路由表。

## 一、需求类型判定信号（识别表，先判定）

| 需求类型 | 识别信号（Issue 标题/正文） | 流程 |
|---|---|---|
| **功能需求** | 「增加 / 支持 / 扩展 / 提供 / 能够 / 需要 / 实现」+ 能力动词 | `feature-flow.md` |
| **Bug 需求** | 「异常 / 报错 / 失败 / 不工作 / 崩溃 / 慢 / 坏了 / X 有问题 / X 不能用」 | `bug-flow.md` |
| **咨询需求** | 「这个项目是干什么的 / 有哪些功能 / 怎么安装 / 怎么部署 / 怎么使用 / 谁负责」 | `consult-flow.md` |
| **任务型需求** | 「提交 PR / 更新 PR / 推送分支 / 定位 Bug / 检视 PR / 审查 / 跑测试 / 构建 / **部署 / 上线 / 资源释放**」 | `task-flow.md` |

**判定优先级**：Bug 关键词 > 任务指令词 > 功能动词 > 咨询意图词；无法判定 → 按功能需求引导（或澄清追问一次）。
**歧义处理**：一句话同时含多种信号（如"提交 PR 且顺便新增功能"）→ 先按主诉求类型处理；其余信号在收敛结论/移交 context 中标注。

## 二、先自主调查再提问（核心原则，功能 & Bug 必须遵守）

**不要不问青红皂白就要求用户提供「现象/复现/期望」等**。VOD 应先基于知识基线/仓库现状调查用户所述场景，尽量理解意图本身。

1. **先调查**（runbook Step 0 基线 + feature/bug-flow 的 tree/contents/pulls/commits 定位）：
   - Bug → 定位相关代码路径/模块/近期提交/历史 Issue，判断可复现性与影响面；
   - 功能 → 看现有能力与结构，判断新增点、是否已有类似实现/在途 PR。
2. **判定分档（收敛门禁核心）**：调查后把歧义分成两类，**只有「工程可推断」才可直接收敛**：
   - ✅ **工程可推断**（碰撞判定、重开清理合理性、吸附网格、实现参数细节；Bug 的代码可定位根因）→ 直接收敛，注明假设让用户确认；
   - ❌ **核心意图歧义**（功能：生成方式二选一/数量/开关取舍 = 用户偏好，代码查不出；Bug：现象含糊到无法确定复现路径、根因多候选且用户意图不明）→ **必须转澄清**，不得收敛/A2A。
3. **后提问**：仅当调查后仍无法清晰化（定位不到、多义、缺关键上下文）才提问；提问结合调查结果、具体、每次 1-3 个、≤3 轮。
4. **少打扰**：能基于调查收敛的直接收敛；仅对工程可推断假设在收敛结论中注明「假设：…」，让用户确认而非空白提问。
5. **澄清即 awaiting-input 触达**：需要用户补充时，**发追问评论 + `grape issues awaiting-input`（显式置 awaiting_input 状态 + 飞书触达）**，然后本轮 `tasks complete`（next_step=`a2a_need_clarify`）收尾；用户 `clarify` 回复后 `awaiting_input → processing`，新一轮再进来继续（参见 `feature-flow.md`/`bug-flow.md` 澄清步骤）。
6. **收敛自检（发布/A2A 前必做）**：收敛结论若出现「可能指 A 或 B」「A/B 两条路径」「暂定/先按…」「疑似 A 或 B」「复现待确认」等并列歧义表述 → **门禁未通过，改走澄清分支**，不发布收敛评论、不 A2A。

## 三、引导要素

### 功能四要素（feature-flow 用）

| 要素 | 判断问题 | 不清晰示例 |
|------|---------|-----------|
| 目标 | 一句话能说清要达成什么？ | "搞一下这个" |
| 现状 | 当前行为/缺失是否明确？ | 未说明当前表现 |
| 期望行为 | 期望的具体行为/场景步骤是否清晰？ | "更好用点" |
| 验收标准 | 是否可验证？ | 无任何可检验描述 |

四要素齐全 → 清晰；任一缺失/含糊 → 需引导（先调查后提问）。

### Bug 六要素（bug-flow 用，作为「调查后仍需补充时」的兜底提问项）

| 要素 | 含义 |
|------|------|
| 现象描述 | 用户实际看到什么（错误信息/异常行为） |
| 复现步骤 | 如何复现（步骤/前置条件） |
| 期望 vs 实际 | 期望应该怎样 vs 实际怎样 |
| 影响范围 | 影响哪些功能/用户、严重程度（P0-P2） |
| 环境 | 版本、平台/OS、浏览器等 |
| 日志报错 | 日志/堆栈/报错片段（如有） |

> ⚠️ 六要素是「调查后仍不清」的提问清单，非默认第一轮——能通过代码/提交/历史线索推断的不要重复问用户。

## 四、结构化收敛模板（评论发布，不改写原始 Issue）

### 功能模板
```markdown
## 目标
{用户想达成的结果，一句话}

## 现状
{当前行为/缺失，结合知识基线描述}

## 期望行为
{清晰描述期望，可含使用场景步骤}

## 验收标准
- [ ] {可验证的验收项 1}
- [ ] {验收项 2}

## 优先级
P0（紧急）/ P1（重要）/ P2（一般）

---
来源：Issue #{n}
auto-submitted by VOD Agent
```

### Bug 模板
```markdown
## 现象描述
{实际看到/报错}

## 复现步骤
1. ...
2. ...

## 期望 vs 实际
- 期望：{...}
- 实际：{...}

## 影响范围
{影响的功能/用户；严重度 P0-P2}

## 环境
{版本/平台/OS}

## 日志报错
{报错/堆栈片段；无则写"待补充"}

## 调查线索（VOD 推断，待确认）
{定位到的模块/提交/疑似根因；未定位到写"未定位"}

---
来源：Issue #{n}
auto-submitted by VOD Agent
```

## 五、strict A2A 动态路由表（本技能独有，交办必用）

> ⚠️ **本技能交办 A2A 目标按需求类型动态决定**，不硬编码 `issue`：

| 需求 | A2A 目标（strict 语义） |
|---|---|
| 部署 / 上线 / 发布 / 运行服务 / 启动应用 / 云资源 / ECS / 容器 | `sre`（跳过 issue/coding/qa，正常行为不算"跨阶段跳过"） |
| 资源释放 / 销毁 / 删除资源 / 回收 | `sre` |
| 开发 / 实现 / 新增 / 修改 / bug 修复 / feature | `issue`（完整 5 节点 issue→coding→qa→sre） |
| 提交 PR / 更新 PR / 推送分支 | `coding` |
| 定位 Bug / 检视 PR / 审查 | `qa` |
| 跑测试 / 构建验证 | `coding`（或 `sre`，视构建/部署） |
| 危险任务（删除分支/项目/Issue、重启环境/停服务、付费/不可逆、直接合并 PR） | **委婉答复，不执行不转交** |

```bash
grape a2a handoff --json '{
  "agent": "issue",
  "payload": {
    "repository": "{owner}/{repo}",
    "account": "{account}",
    "issue_number": {n},
    "pr_number": 0,
    "context": "需求已结构化收敛（评论发布）：{摘要}。请继续 spec 设计/打标签/排里程碑/分配责任人。"
  }
}'
```
（部署/资源释放类把 `agent` 换成 `sre`；任务安全类按上表换成对应 agent。）

> ⚠️ `issue_number` 必填；无法确定则不调 A2A，在评论说明。A2A 前查 pipeline 已含目标 `a2a_event` → 不重复 A2A。A2A 失败重试 ≤3 次；仍失败 → 评论说明 + next_step 标注人工介入。
